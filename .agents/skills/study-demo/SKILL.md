# 学习型 Demo

让每个例子能运行、能触发关键行为、能观察结果，并解释为什么得到该结果。默认优先提供可操作的页面：当页面有助于触发行为、比较状态或观察结果时，即使核心概念属于后端或数据库，也提供页面和真实可调用的后端接口。不要仅因可以通过终端运行，就把适合页面观察的 demo 做成纯命令行实验。若用户明确要求纯命令行或单端实现，遵守该范围，不补造另一端；若判断页面对当前 demo 没有实际帮助，在实施前告知用户原因及替代的操作和观察入口。沿用各仓库技术栈与目录规范，选择小而真实、便于比较的例子；标明教学简化，不将过时做法当作生产推荐。

## 展示与讲解

- 每个例子独立说明它解决的问题、触发条件及相关概念；沿请求或操作的执行顺序解释关键代码、框架机制和处理器，最后解释预期结果。讲解靠近对应例子，指出相近做法的区别与适用边界，不堆砌无关文档。
- 提供可操作的入口和有助于学习的实际结果，如输入输出、状态码、响应头、错误或界面状态。无法在页内呈现的行为提供合适的操作入口。
- 在实际结果旁解释关键字段和现象，包括失败、无响应或连接中断，标明对应代码步骤与机制。操作前应能读懂预期，操作后能对照实际；验证时逐例检查讲解是否准确、可理解。
- 后端接口在处理请求时也打印能与页面操作对应的日志：示例名称、关键步骤、结果或错误。不要只依赖通用访问日志，也不要记录密码或令牌。

## 代码结构入口（有 Web 页面时）

每个 demo 页面使用位置、文案和交互方式统一的”代码结构”按钮，打开可关闭的全屏审阅弹窗，布局参照 GitHub PR 文件审阅。header 为 flex 左右布局：左侧直接放大标题（32px）和一句话描述，不加分类 kicker（如 “EXPRESS / HTTP” 等）；右侧只放”代码结构”和”知识点讲解”两个按钮，不放任何统计 Badge（如”N 个接口””N methods”等）。header 底部加 1px 浅色分隔线（`#e3eaec`），与下方内容区分隔。左侧是可逐级展开、收起、跳转的目录树，默认宽 360px，可拖动分隔条；左栏占满弹窗可视高度，内容溢出时在栏内显示细滚动条。窄屏时目录树置于上方并保持固定高度。右侧按文件展示当前完整源码，带行号与语法着色，不显示修改前后对比，也不限制文件内容高度。

每个文件提供“已读”复选框，勾选时收起代码，取消时重新展开。说明目录和关键文件职责、前后端对应关系；列明数据库变更（新建或复用的表、迁移及用途），没有变更也须注明，保持信息与实现一致。新增 demo 时同步登记源码加载范围和开发环境预览白名单，验证每个文件均可加载。不要维护手写源码副本或泄露敏感信息；单端 demo 只展示实际存在的部分。

## 知识点讲解入口（有 Web 页面时）

每个 demo 页面在“代码结构”按钮右侧再放一个“知识点讲解”按钮，点击打开可关闭的全屏弹窗，以 Markdown 形式展示该 demo 的知识点。按钮统一使用 `apps/web/src/components/DemoKnowledgeDialog`：`content` 传入用 Markdown 编写的知识点内容，`demoName` 传入弹窗标题展示的名称。

知识点内容围绕“核心概念、机制、关键代码、边界与误区”组织：说明该 demo 解决的问题与触发条件，讲解关键机制并给出对应代码，用表格或列表对比相近做法的区别与适用边界，指出常见误区。内容须与页面演示、代码结构和实际结果保持一致，不堆砌无关文档。新增 demo 时同步补充该页面的知识点 Markdown 与“知识点讲解”按钮。

## 前后端接口契约（涉及跨仓库接口时）

- 新增供 `study-react` 调用的 `study-nodejs` 接口前，检查 `study-nodejs-schema` 的现有契约；在其 `apis/<功能>/` 定义或扩展请求参数、请求体、成功响应及预期错误响应的 Zod schema 和接口描述。无请求体的接口也要明确响应结构，不要因 demo 简单就省略契约。
- 后端用契约校验输入并保持输出一致；前端从同一契约获得类型和结果解释，避免两端各自维护不一致的手写请求/响应模型。验证契约生成、构建和两端的实际接入，不要只添加未被消费的 schema 文件。
- 若用户明确将工作限定为单仓库，或契约包的构建、依赖接入确实阻碍当前任务，在实施前告知用户影响与替代方案，不要默默绕开共享契约。无需跨仓库接口的纯单端 demo 不因此补造接口或 schema。

## 后端与数据库（涉及后端时）

- 将同一 demo 的路由、业务逻辑、模板、示例静态文件放在同一功能目录，与 Web demo 对应，但遵循后端命名（如 `express/response-methods`）。目录内按职责适度拆分，只有跨 demo 复用的代码放公共目录。
- PostgreSQL 查询、表结构、迁移、联调统一使用 `study_nodejs` 数据库，以 `DATABASE_URL` 配置连接，不提交真实凭据；不要使用旧的 `lqd`、默认 `postgres` 或其他项目数据库。
- 建表、迁移或可能修改数据的验证前，确认 `current_database()` 是 `study_nodejs`。默认单元测试使用注入或模拟，不连接真实数据库；真实数据库测试需显式启用并限于该库，不清空或重建已有数据。
- 涉及数据库时先检查 `study_nodejs` 是否有适用表；仅在不改变其他 demo 所依赖的结构、数据或结果时复用。写入和清理仅作用于本 demo 数据，否则使用专用表。
- 新表用小写 `snake_case`：`demo_<模块名>_<表用途>`。模块名取前端 demo 页面目录最后一级转为 `snake_case`，并与后端功能目录对应；仅有后端时取后端功能目录最后一级。例如 `pages/Express/ResponseMethods` 对应 `demo_response_methods_<表用途>`，事务部门表可命名 `demo_transaction_departments`。表用途使用业务含义，不以 `001` 等编号作固定后缀。

## 前端代码组织（有 Web 页面时）

- 常量放到 `constants.ts`，util 方法放到 `utils.ts`，提取的类型放到 `types.ts`；这些文件就近存放在所属页面或组件目录下，不跨目录共享。
- 组件适当拆分，每个组件单独一个文件，不要把多个组件堆在 `index.tsx` 里；子组件放在同目录的 `components/` 下，hook 放在 `hooks/` 下。
- 只有当前页面用到的代码才放在该页面目录；跨 demo 复用的才提升到公共目录。

## 前端页面设计（有 Web 页面时）

- 编写 demo 的 Web 页面时，先完整读取 `frontend-design` skill 的 `SKILL.md`，并按其流程执行：先形成围绕该 demo 学习主题的设计方案（色彩、字体、布局、原则），再对照需求复核该方案是否真正由主题推导而来，最后实现并在交付前批判性自检、去掉不服务于内容的多余装饰。
- 把视觉选择落到该 demo 的具体学习主题上：页面主视觉、配色、字体与布局应来自被演示的概念、机制或数据，而不是通用模板的默认观感。避免 AI 生成的常见套路（暖米色背景＋高对比衬线大标题＋陶土色点缀、近黑背景＋单一荧光色、无差别圆角卡片＋同一软阴影＋渐变装饰、全大写 eyebrow 标签＋中点连接的 meta 串等）；确需使用这些观感时，须能说明它由主题推导而来，而非随手可得。
- 建立并遵循一个小型设计系统，并达到可访问性底线：以 4px 为基准的间距刻度、不超过三步且随层级变化的圆角、最多两级用色板暗色而非 `rgba(0,0,0,.1)` 的阴影、明确的断点与重排规则、≥4.5:1 的正文对比度与可见焦点态。学习内容优先：代码、状态对比、机制说明与结果呈现的可读性和可观察性高于装饰，任何设计都不能削弱这些信息。
- 保持现有统一入口与约定不动：`代码结构`、`知识点讲解` 弹窗的位置、文案、交互与既有视觉规范保持一致；新增页面与弹窗之间维持统一的视觉语言，不引入与既有约定冲突的观感。
- 文案即设计：按钮、提示、状态说明用用户能直接理解的平实语言，动作与结果用词一致（如“保存”对应“已保存”），错误与空状态说明发生了什么以及如何修正，不堆砌空泛的营销化描述。

## 验证与交付

验证构建、静态检查和关键交互，最终说明运行方式及未验证部分。数据库验证遵守上述连接和数据边界。
